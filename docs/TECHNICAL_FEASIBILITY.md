# Technical feasibility

This assessment describes SafeSeat 0.1.0 and the research target: one Windows 11 Pro installation on one physical PC, two monitors, two keyboards and two mice. Physical operation of that configuration remains **NOT TESTED** in this public release.

## Gate decision

**NO-GO for the full arbitrary-application requirement using the supported design investigated here.** Raw Input can identify the device that produced an event. It does not supply a second independent Windows foreground focus, native pointer or interactive console seat. The reviewed APIs do not provide the missing device-to-independent-desktop binding. No reproducible physical evidence establishes simultaneous, independent input into unmodified Chrome, Word or other generic applications. Acceptance tests 5–7 remain NOT TESTED.

**GO for a bounded, user-mode controlled application prototype.** SafeSeat can enumerate devices and monitors, identify event sources in an explicit no-text observation mode, and route observed device events into two state models owned by SafeSeat. Rendering those models in two application windows is an application feature, not a second Windows user session. A passing simulated router test establishes only the state-model behavior tested; it cannot establish physical USB behavior, Windows licensing rights or arbitrary-application compatibility.

These conclusions distinguish documented constraints from an engineering decision. They are not a claim that every conceivable future platform feature is impossible. A new proposal would need a documented routing mechanism, a license permitting its use and a repeatable physical test before changing this decision.

## Documented platform facts

| Area | Microsoft documentation says | Consequence for this project |
| --- | --- | --- |
| Device identity | Raw Input identifies the reported input collection, including multiple devices of the same class. [Raw Input overview](https://learn.microsoft.com/en-us/windows/win32/inputdev/about-raw-input) | The receiving application can assign collections to its own seats. Collection identity alone does not verify physical ownership or device count. |
| Keyboard focus | Normal keyboard messages go to the foreground thread's focused window; focus shifts between windows. [Keyboard input overview](https://learn.microsoft.com/en-gb/windows/win32/inputdev/about-keyboard-input) | Monitoring two keyboards does not turn two arbitrary windows into independent input destinations. |
| Input desktops | Only one desktop in the interactive window station is the active input desktop at a time. [Desktops](https://learn.microsoft.com/en-us/windows/win32/winstation/desktops) | Creating another desktop does not make two desktops concurrently interactive on separate physical monitors. |
| Window stations | The interactive station contains the keyboard, mouse and display. Other window stations are noninteractive; remote sessions have their own interactive stations. [Window stations](https://learn.microsoft.com/en-us/windows/win32/winstation/window-stations) | A new user-mode station is not a supported second local seat. |
| Sessions | Windows Enterprise multi-session supports concurrent interactive sessions and is a separate virtual edition intended for Azure Virtual Desktop. Microsoft's FAQ restricts production use outside that service. [Enterprise multi-session FAQ](https://learn.microsoft.com/en-us/azure/virtual-desktop/windows-multisession-faq) | This capability cannot be assumed for Windows 11 Pro, nor added through a SafeSeat preference. |

## License boundary

The [Windows 11 license terms published by Microsoft](https://www.microsoft.com/content/dam/microsoft/usetm/documents/windows/11/oem-%28pre-installed%29/UseTerms_OEM_Windows_11_English.pdf) (April 2024), section 2(a), grant use of the instance by one person at a time. Section 2(d)(iv) addresses virtual instances and additional licenses. Those terms distinguish OEM/retail from volume licensing. Review the agreement applying to the intended installation. The [commercial Windows Desktop Operating System Product Terms](https://www.microsoft.com/licensing/terms/product/WindowsDesktopOperatingSystem/all) also impose a one-user-at-a-time rule in the device-license section; separate entitlements can have different rights.

**Project decision:** do not describe Windows 11 Pro as a licensed two-user platform or present an in-app demo as a licensing exception. Use automated simulation or one operator exercising two device sets for initial experiments. A simultaneous two-human test requires applicable terms that permit that use. A second Windows VM is a separate OS instance and requires its own applicable rights; it also changes the same-installed-OS requirement. Deployment rights must be reviewed separately from the software experiment.

## Approach comparison

The behavior and effort estimates below are engineering assessments derived from the cited API contracts. Physical compatibility and performance remain NOT TESTED.

| Approach | Input isolation and generic apps | Security and licensing | GPU/audio and effort | Decision |
| --- | --- | --- | --- | --- |
| A. Same interactive desktop, unmodified apps | Raw Input separates observations in cooperating code. Ordinary windows still share native input activation. No supported per-device focus assignment was established. Browser profiles separate profile data, not input seats. | One user security context, shared clipboard and desktop. No security isolation between SafeSeat's internal seats. Windows license review is still required. | Native GPU access remains shared. Audio endpoints are not automatically assigned by physical keyboard. Launch, dialog, fullscreen and focus handling would need application-specific behavior; high effort cannot remove the missing input mechanism. | NO-GO for the full target. No focus-thrashing experiment. |
| B. Separate sessions or user-created desktops in one OS | A supported remote session architecture can isolate a session's UI, but user-created desktops provide only one active input desktop. Pro was not established as supporting the required concurrent local seats. | Session isolation is stronger than two app models. Enabling unsupported concurrent sessions or patching RDP is excluded. Enterprise multi-session/RDS rights and platform requirements differ from Pro. | Session display/audio redirection and GPU capacity need their own deployment and workload tests. Assigning four local USB devices to two simultaneously visible local sessions is a separate unsolved requirement here. Very high effort and different platform requirements. | NO-GO under this project's platform and free-dependency constraints. |
| C1. User-mode controlled workspaces | SafeSeat owns both renderers and can route raw events by device into independent state. Only cooperating SafeSeat controls participate. Unmodified external applications do not inherit this routing. | Standard user; observation is opt-in and stops outside the app. Both states remain in one process/security context. Review the license boundary before two-human use. | WPF rendering shares the host graphics stack. No separate audio implementation. Moderate implementation effort; physical validation remains essential. | Selected safe prototype. |
| C2. Separate VM per user, using open-source virtualization software | A guest can have its own focus and pointer after exclusive device assignment is solved. A host window capturing the shared pointer alone does not establish device isolation. | Stronger OS separation, additional OS/app license rights, new trust and configuration work. No VM installation, passthrough driver or OS feature change is part of this prototype. | GPU acceleration, USB exclusivity, audio routing, latency and game compatibility depend on host/guest support. High effort; cannot promise universal gaming behavior. | Separate research alternative; fails the same-installed-OS requirement. |

For the VM alternative, [QEMU's license documentation](https://www.qemu.org/docs/master/about/license.html) identifies GPLv2 and component-specific licenses. Its [USB documentation](https://www.qemu.org/docs/master/system/devices/usb.html) limits real host USB support by host OS. Neither source establishes safe, driver-free exclusive USB assignment for the target Windows 11 Pro deployment. QEMU and VM setup are outside SafeSeat's implemented dependencies and behavior.

## API review and implementation boundary

### Raw devices

| API/contract | Required handling and reviewed limitation |
| --- | --- |
| [RegisterRawInputDevices](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-registerrawinputdevices) | Register one receiving window per device class within this process. `RIDEV_DEVNOTIFY` enables arrival/removal messages. Removal requires `RIDEV_REMOVE` with a null target. Check errors. Microsoft's [Using Raw Input](https://learn.microsoft.com/en-us/windows/win32/inputdev/using-raw-input) examples show registration, device information and packet processing. |
| [RAWINPUTDEVICE flags](https://learn.microsoft.com/en-us/windows/win32/api/winuser/ns-winuser-rawinputdevice) | The sole observation flag is `RIDEV_DEVNOTIFY`; delivery remains foreground-application only. Neither `INPUTSINK` nor `EXINPUTSINK` is requested. One receiving HWND serves the two windows owned by this application. No `NOLEGACY`, `CAPTUREMOUSE`, exclusion or hotkey-suppression flags are used. Native Windows input continues. |
| [WM_INPUT](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-input) | `RIM_INPUT` (0) means input occurred while the application was foreground; this is not a requirement that the receiving HWND itself be active. The observer rejects `RIM_INPUTSINK` before reading packet data. Foreground messages still require default-window-procedure cleanup. |
| [GetRawInputData](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getrawinputdata) | Query required size, bound allocations, check copied length/error values and parse pointer-sized headers correctly. Data inspection occurs only after explicit running/current-foreground checks and the foreground-generation-code check; background packet contents are not decoded. |
| [GetRawInputDeviceList](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getrawinputdevicelist) | Enumerate with count/query/retry handling because devices may change during enumeration. RDP input devices are not listed. Remote operation is not physical two-seat proof. |
| [GetRawInputDeviceInfoW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getrawinputdeviceinfow) | The implementation requests `RIDI_DEVICENAME`, which uses character counts; device class comes from the device list. The API also supports `RIDI_DEVICEINFO`, whose structure requires `cbSize`, but that query is not currently used. An interface path is not a promise of permanent physical identity. |
| [WM_INPUT_DEVICE_CHANGE](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-input-device-change) | Handle arrival/removal, refresh the inventory and stop an active run before asking for reassignment. A transient `hDevice` is not a persisted identity. |

Identity policy is an engineering safeguard: persist a hash of the reported interface path, never the runtime handle; show short identifiers and device class in the UI. A hash conceals the literal path but is not guaranteed anonymous or stable. Identical devices, composite HID collections, USB port changes and Bluetooth reconnects require manual confirmation when identity is ambiguous. Do not silently give a new or ambiguous device another seat's assignment.

A device-change notification or unknown input handle disables packet acceptance before inventory refresh. A changed handle/identity map found by a live refresh also pauses routing. Cleanup and a fresh explicit Start are required before the updated mapping can accept input. Handle identity remains cached between notifications; reuse of an already-known handle before notification has not been validated on physical Windows hardware.

For readable names, [SetupDiOpenDeviceInterfaceW](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdiopendeviceinterfacew) and [SetupDiGetDeviceRegistryPropertyW](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdigetdeviceregistrypropertyw) expose interface/device information and friendly-name/description properties. The implementation uses these as read-only inventory queries and closes its information set; it does not install or configure a device.

### Displays and placement

[EnumDisplayMonitors](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumdisplaymonitors) enumerates logical monitor handles and can include pseudo-monitors. [GetMonitorInfoW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getmonitorinfow) provides monitor/work-area geometry. [QueryDisplayConfig](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-querydisplayconfig) can provide display-path topology; it is a researched extension, not a claim that this prototype identifies permanent monitor serial numbers. Enumeration and source names alone do not prove that two independent physical panels are attached. Mirrored displays, disconnects, negative coordinates and changed DPI require explicit validation.

The current inventory also calls [EnumDisplayDevicesW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumdisplaydevicesw) with `EDD_GET_DEVICE_INTERFACE_NAME` and hashes the returned display-interface identity. This improves assignment labels, but remains a best-effort identity that needs reconnect/clone/dock tests. It does not replace topology validation.

The selected prototype positions only its own test windows and keeps virtual pointers in their own canvas bounds. [SetWindowPos](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowpos) changes a window's geometry/Z order; `SWP_NOACTIVATE` avoids requesting activation. Moving a window to Monitor B does not create an input seat. Verify physical placement and mixed-DPI behavior manually before counting the display test as passed.

Launch the generated `SafeSeat.exe` apphost so its `PerMonitorV2` manifest applies. Microsoft recommends configuring process DPI awareness through the [application manifest](https://learn.microsoft.com/en-us/windows/win32/hidpi/setting-the-default-dpi-awareness-for-a-process). Running the managed DLL under a different executable does not establish the intended apphost DPI behavior. If Windows policy refuses the executable, stop; do not switch hosts or weaken policy to continue.

### Foreground, processes and lifecycle

[GetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getforegroundwindow) may return null during activation changes. [GetWindowThreadProcessId](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindowthreadprocessid) identifies the creating process. SafeSeat's main window checks for a known SafeSeat foreground process before calling the raw-packet reader; uncertainty stops observation. The observer library additionally requires `RIM_INPUT` before any `GetRawInputData` call, but relies on its host for the current-foreground ownership check. [WM_ACTIVATEAPP](https://learn.microsoft.com/en-us/windows/win32/winmsg/wm-activateapp) reports cross-application activation/deactivation; SafeSeat stops on deactivation. A 33 ms dispatcher timer also checks ownership, but scheduling can delay it, so this is not a guaranteed 33 ms stop bound.

[WTSRegisterSessionNotification](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsregistersessionnotification) is needed to receive [WM_WTSSESSION_CHANGE](https://learn.microsoft.com/en-us/windows/win32/termserv/wm-wtssession-change), including lock/disconnect. SafeSeat registers its own HWND with `NOTIFY_FOR_THIS_SESSION`, refuses either observation mode when registration is unavailable, and calls [WTSUnRegisterSessionNotification](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsunregistersessionnotification) when closing. A handler for the message alone would be insufficient. [WM_POWERBROADCAST](https://learn.microsoft.com/en-us/windows/win32/power/wm-powerbroadcast) reports suspend/resume. Display/device changes also end the active run. Session and foreground notification code still need real lifecycle tests.

[CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw) starts a process in the caller's security context; a new process is not a new independent input session. [EnumWindows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumwindows) covers top-level desktop-app windows, not every child/control. [Window features](https://learn.microsoft.com/en-us/windows/win32/winmsg/window-features) distinguishes owned popups, children and active windows. **Inference:** process IDs and initial window placement cannot guarantee all later dialogs, brokered processes and fullscreen windows stay within a seat. Generic app launching/tracking is therefore outside the implemented prototype.

### Rejected forwarding mechanisms

| Mechanism | Why it does not establish the requested independence |
| --- | --- |
| [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) | Inserts synthetic events serially into the keyboard/mouse input stream, is subject to UIPI and has no per-seat target-window argument. It does not create two native focus contexts. |
| [PostMessageW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-postmessagew) | Posts a message to a target thread's queue and is subject to UIPI. A posted `WM_KEYDOWN` is not a documented universal substitute for the recipient's native input, IME, device state or activation behavior. Any success with a selected control would be application-specific evidence only. |
| [SetForegroundWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) | Changes foreground activation and has documented calling restrictions. Repeatedly switching it would change the other person's focus and explicitly fail the task. |
| Two drawn cursors | Application drawings do not provide independent system hit testing, capture or activation. They work only for controls whose input SafeSeat owns. |

No input forwarding, injection, focus thrashing, global keyboard/mouse hook, driver or protected-process workaround is implemented or proposed for execution. WPF's message hook on SafeSeat's own HWND is how the application receives its window messages; it is not a global input hook.

## Scope that needs evidence

The controlled input model is deliberately limited to the standard US English layout, per-device modifier/key-up state, repeated key-down events, bounded ASCII demo text, relative virtual pointer movement, button state and a vertical wheel panel. [GetKeyboardLayout](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeyboardlayout) checks the UI thread's active layout; the implementation requires its standard US identifier and stops the controlled run if it changes. Per-seat Caps Lock starts off each run and can differ from physical keyboard LEDs. Ctrl/Alt/Windows-key combinations are excluded from text entry; OS shortcuts remain native. Dead keys, Unicode/IME composition, AltGr, clipboard integration, full text editing, numpad/Num Lock behavior, absolute pointing devices and horizontal wheel routing are unsupported. High-rate mice, composite HIDs, lock/suspend timing, display hotplug and simultaneous physical operation remain manual tests.

**Observe sources (no text)** is a separate explicit opt-in mode. Like the controlled demo, it receives foreground-application events only. It needs an owned foreground window but does not require two assigned monitors or the US layout. It selects the event's device row and shows only class, short hashed identifier and action kind. It does not translate keys or start the text router. This provides a way to distinguish identically named devices without adding a persistent input log.

Within its own WPF windows, SafeSeat handles native Space/Enter key events to keep a focused UI button from restarting/stopping the run while those keys are routed into demo text. Escape remains an immediate local Stop, and system shortcuts remain native. This is local UI behavior, not global input interception.

Performance statistics, when explicitly enabled, are aggregate in-memory measurements of this process and event-processing time. They are not end-to-end USB-to-photon latency or GPU/audio/game compatibility results. Follow [the acceptance procedure](ACCEPTANCE_TESTS.md) for physical testing and consult the public [verification report](VERIFICATION_REPORT.md) for the scope of recorded software checks.

The default console suites contain 36 core checks and 210 adapter checks. Simulated lifecycle tests use a fake backend and do not start production input registration. Their results cannot establish physical keyboard/mouse counts, notification ordering, visible placement or simultaneous third-party application independence. Source boundaries can be inspected in [the observer](../src/SafeSeat.Windows/RawInputObserver.cs), [inventory](../src/SafeSeat.Windows/WindowsInventory.cs), [router](../src/SafeSeat.Core/SeatRouter.cs) and [owned seat renderer](../src/SafeSeat.App/SeatWindow.cs).
