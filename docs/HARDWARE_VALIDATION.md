# Hardware identification and validation

**Physical two-seat operation remains NOT TESTED.** This guide turns inventory hints into a repeatable operator check. It contains no machine-specific inventory or acceptance sign-off. Device collections and candidate groups do not establish a physical device count or independent generic Windows applications.

## Three different kinds of evidence

| Level | What it establishes | What it does not establish |
| --- | --- | --- |
| Raw Input collection | Windows exposes an input endpoint with a class and hashed interface `Id`. A physical HID can expose multiple top-level collections. | The number of objects on the desk, their human owner or permanent identity. |
| Candidate PnP group | Matching hashed `CandidateGroupId` values suggest related Windows device nodes. Optional `TransportHint` and `CorrelationNote` explain the metadata and its uncertainty. | A verified physical-device count, an exclusive seat or permission to merge assignments. |
| Physically confirmed mapping | An operator sees a particular labelled keyboard/mouse produce the expected source row and repeats the check after reconnect. | A second Windows focus, third-party-app independence or behavior on untested hardware. |

Microsoft documents that one HID report descriptor can contain multiple [top-level collections](https://learn.microsoft.com/en-us/windows-hardware/drivers/hid/top-level-collections). Its [Container ID model](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/container-ids) groups related device nodes. [DEVPKEY_Device_ContainerId](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/devpkey-device-containerid) supplies the grouping GUID; SafeSeat queries it read-only using [SetupDiGetDevicePropertyW](https://learn.microsoft.com/en-us/windows/win32/api/setupapi/nf-setupapi-setupdigetdevicepropertyw) and exposes a hash, not the GUID or raw device path. Missing properties or access denial remain unknown; do not elevate to obtain them. Metadata failure does not itself disable an otherwise identifiable raw collection.

SafeSeat calls this a **candidate** because metadata is not a physical observation. Microsoft describes [container implementation problems](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/troubleshooting-the-implementation-of-container-ids), including one device appearing in multiple containers. Matching a group does not change a collection's `Id`, assignment or routing. A null group is not proof that a device is absent. `TransportHint` is a limited [enumerator-name](https://learn.microsoft.com/en-us/windows-hardware/drivers/install/devpkey-device-enumeratorname) hint; an HID enumerator alone does not identify its underlying connection.

## Topology caveats

- **Composite USB devices and receivers:** Windows supports [USB devices with multiple interfaces](https://learn.microsoft.com/en-us/windows-hardware/drivers/usbcon/enumeration-of-the-composite-parent-device). Multiple rows can belong to one keyboard or receiver. For a receiver serving several peripherals, a shared candidate group must not automatically put all its rows on one seat. If two mice produce the same raw source row, SafeSeat cannot distinguish them; record that blocker and stop assigning them as separate seats.
- **Bluetooth and changing connections:** pairing, a different port/dock, reconnects or driver changes can alter identities or grouping. Use already paired devices. Recheck manually; SafeSeat does not pair devices or change drivers.
- **Virtual and remote devices:** a friendly HID name or container hash does not certify physical origin. Microsoft's [Raw Input device-list reference](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getrawinputdevicelist) says RDP input devices are excluded from that list. A remote session therefore cannot establish local physical topology. Root/software/unknown hints remain unverified.
- **Displays:** two logical labels, mirrored output or a saved monitor assignment do not prove two independently usable panels. Confirm extended mode and both physical panels. Console enumeration from a thread without per-monitor DPI awareness can use virtualized coordinates; it does not verify the apphost's visible placement.

## Safe operator procedure

1. Read [Safety and recovery](SAFETY_AND_RECOVERY.md), save work, back up important files and prepare its owner-controlled restore-point precaution. Use a standard account and expendable text. Begin with one operator; review [Windows use rights](TECHNICAL_FEASIBILITY.md#license-boundary) before a simultaneous two-human run. No driver, elevation or OS-policy change is part of this procedure.
2. Label the intended devices physically, for example A keyboard, A mouse, B keyboard and B mouse. Note any shared receiver or built-in touchpad. Keep a native recovery device available. Launch SafeSeat stopped and select **Refresh inventory**. Read collection/group counts as different observations; group labels are hints for finding related rows.
3. Keep SafeSeat foreground. Select **Observe sources (no text)**. Operate exactly one labelled device while leaving the others still. For a keyboard, press/release an expendable ordinary key; for a mouse, move it slightly. The matching source row should become selected. Note only the label-to-short-ID association and whether it matched, never the key or event stream.
4. Press **Escape** before assigning. Moving a mouse to click Stop can select that mouse's row, so do not mistake that row for the keyboard just checked. Confirm the selected row/class, then use **Assign Seat A** or **Assign Seat B**. Repeat source observation and Escape for every intended device. If multiple physical devices resolve to the same row, or a device's ordinary actions span incompatible rows, leave the affected slot unconfirmed; do not guess from names or container membership.
5. Require one confirmed keyboard collection and one confirmed mouse collection per seat. Choose different available monitor identities and inspect both panels in extended mode. Save only after review. `profiles/default.json`, beside the executable, stores `Version`, `DeviceAssignments` keyed by collection `Id`, and `MonitorAssignments` keyed by seat. Candidate groups do not replace those assignment keys. Reload the profile and repeat identification after topology changes.
6. With two confirmed panels/device sets available, select the standard US English layout, release held keys and choose **Start controlled demo**. While either owned window is active, exercise both text states, virtual pointers, counter/clear controls and wheel panels. One operator testing sequentially establishes mapping only. Simultaneous physical independence requires the separate timed procedures in [acceptance tests 3–4](ACCEPTANCE_TESTS.md#3-controlled-in-app-keyboard-isolation), with operator count recorded and appropriate rights for two-human use.
7. Test recovery using expendable activity: Escape, native Stop, leaving SafeSeat, device disconnect/reconnect, monitor changes, session lock/unlock and suspend/resume. Expect stopped status, closed seat windows, cleared temporary text/held state and an explicit new Start after review. Follow [acceptance tests 8 and 10](ACCEPTANCE_TESTS.md#8-device-display-and-lifecycle-changes). Keep unexercised cases NOT TESTED; one successful unplug does not cover every lifecycle event.
8. Stop and exit after the check. Confirm normal native input remains usable. If cleanup reports a Win32 error, record the code and exit; use native Task Manager if necessary. Do not add a filter driver, enable background observation or change security protections to continue.

## Privacy and result recording

Both observation modes are explicit and foreground-only. They do not request `INPUTSINK`; background-generation packets are rejected before data is read, and the application checks current foreground ownership. Source mode shows class, short identifier and action kind without translating or buffering text. Foreign-app activation and session notifications end the run; real lifecycle delivery still requires testing. There is no persistent keystroke logger, screen capture or background server. Hashes are not guaranteed anonymous, so share only the evidence needed.

Record date/time, build/revision, local or remote context, labelled-device-to-collection matches, candidate metadata availability, panel count/layout, operator count, mismatch counts and recovery outcomes. Keep text, raw paths, serial numbers, credentials, screenshots and per-key timestamps out of the record. Fake-native lifecycle tests and simulated streams establish software behavior only. Update an acceptance result only for a procedure actually completed on the intended hardware.

Operator identification and visible placement require a permitted run of the generated `SafeSeat.exe` under the existing protections. If policy blocks that executable, record the blocker and stop without an alternate host or policy workaround. Generic Chrome/Word/game tests 5–7 remain blocked by the [platform design](BLOCKERS_AND_ALTERNATIVES.md), regardless of how many candidate groups inventory reports.
